# 第一個專案：從上線清單到驗收成果 {#first-project}

本教學帶你從首次登入走到獨立審查通過。範例專案是「產品上線準備」（`LAUNCH`），任務名稱是「整理產品上線清單」。畫面和欄位名稱對應已安裝的 Ordivant；你所在組織的專案、模型供應商和政策可能不同。

## 開始前 {#before-you-begin}

開啟管理員提供的平台網址。若要自行安裝 Ordivant，請先完成[安裝指南](../containers.md)，再開啟本機或組織網址。試用流程不需要先設定模型金鑰；下面的人工路線不需要金鑰。Pi Durable 自動執行則需要管理員啟用 Runtime 並設定供應商與模型。

![Ordivant 登入畫面](/screenshots/login-zh-TW.png)

## 以管理員或受邀成員登入 {#sign-in}

全新環境由第一位使用者開啟工作區，選擇「建立管理員帳號」。輸入姓名、電子郵件、至少 12 個字元的密碼並再次確認，再送出。請將一次性復原碼安全保存。系統沒有預設帳號或密碼。

若你是受邀成員，請在登入頁選擇「接受邀請」，輸入管理員交給你的一次性邀請碼，再自行設定密碼。邀請碼 24 小時後過期，且只能使用一次。使用 SSO 的成員則透過企業登入按鈕登入。能登入不代表自動取得所有產品或專案的存取權；請見[團隊設定](team-setup.md)。

## 建立上線專案 {#create-project}

1. 在產品切換器選擇 **Work**。在專案選擇器中選擇「建立專案」。只有 Identity 管理員可以建立 Work 專案。
2. 輸入以下內容：

   | 欄位 | 範例 |
   | --- | --- |
   | 專案代碼 | `LAUNCH` |
   | 專案名稱 | `產品上線準備` |
   | 描述 | `規劃、追蹤並審查產品上線前需要完成的工作。` |
   | 團隊 ID | 除非管理員提供實際團隊 ID，否則留白。 |
   | 預算上限 (USD) | 除非組織使用專案預算，否則留白。 |

3. 送出「建立專案」。專案選擇器和頁面標題應顯示 `LAUNCH` 與「產品上線準備」。

若你是一般成員而無法建立專案，請管理員建立專案，並授予你的 Work 角色和專案範圍。切換至 Work 不會自動取得存取權。

## 選用：加入有版本的 Knowledge 規格 {#knowledge-specification}

如果上線需求需要負責人、版本歷程和可追溯來源，可以選用 Knowledge。

1. 切換至 **Knowledge**。Identity 管理員選擇「新增 Space」，以代碼 `LAUNCH`、名稱「產品上線準備」和簡短描述建立空間。接著由管理員授予相關人員 Knowledge 角色和該 Space 範圍。
2. 選取 `LAUNCH` Space，選擇「新增文件」。例如標題填「上線準備規格」，摘要填「首次上線審查需要的要求與證據」，標籤填 `launch` 和 `readiness`。
3. 在「正文（Markdown）」輸入實際規格，包含決策、負責人、日期與已知來源資料。適當加入來源引用的標籤與 URI，然後選擇「建立文件」。閱讀畫面應顯示 `v1`、正文與來源引用。
4. 日後要修改時，開啟最新版本並選擇「發佈新版本」。確認「預期目前版本」，編輯標題和正文，填入變更摘要後發佈。已發佈版本不能修改；新內容會成為下一個版本。

來源引用中的 URI 是引用資料；輸入 URI 不會自動讀取或匯入頁面內容。請貼上或撰寫你獲准使用的內容，或另外設定已核准的檢索／工具整合。請見[Knowledge 指南](knowledge.md)。

## 為自動 Run 設定模型連線 {#configure-model}

人工路線可跳過本節。只有 Identity 管理員能編輯組織模型連線。請向供應商或部署管理員確認受支援的 HTTPS API base URL 和正確的模型 ID。請直接在表單輸入自己從供應商取得的金鑰；不要複製指南中的金鑰、把金鑰放入任務或傳給 Agent。

1. 在 **Work** 開啟「模型連線」。
2. 選擇「新增 Provider」，輸入唯一的 Provider ID、顯示名稱、供應商的「HTTPS API base URL」，並在「API Key」欄位輸入你自己的金鑰。例如網址格式可能是 `https://api.example.com/v1`；這是示例網域，不是可用的供應商網址。
3. 依供應商資料新增模型 metadata：正確的 Model ID、顯示名稱、Context window、最大輸出 tokens 與支援的推理強度，然後啟用 Provider。
4. 開啟組織預設模型，選擇 Provider 和 Model 並儲存。建立 Pi Agent 時應可選取該模型。已儲存的金鑰不會再以明文顯示；只有更換時才輸入新金鑰。

![模型連線設定](/screenshots/models-zh-TW.png)

若沒有設定可用的 Provider 或模型，派發的 Run 可能會標示 **DEMO**。DEMO 使用確定性的示範回覆，不會呼叫付費模型，也不會產生真實上線交付物。不要把示範輸出或回報成本當成已完成的任務。請見[模型連線](../model-usage.md)與[Run 與自動化使用指南](../execution-usage.md)。

## 在此專案建立 Pi Durable Worker Agent {#create-agent}

Identity 管理員或 Work Manager 可以管理 Agent。先確認 Work 目前選取的專案是 `LAUNCH`；建立表單會把目前選取的專案授權給新 Agent。Agent 表單沒有 Project 欄位。

1. 開啟「Agent 名錄」，選擇「新增 Agent」。
2. 名稱輸入 `Launch checklist worker`；「Agent 角色」選擇「執行者」，「Runtime」選擇「Pi Durable」。若團隊尚未發布適合的不可變範本，請將「Agent 範本版本」留白。
3. 在「能力標籤」加入 `launch-readiness`、`research`、`documentation` 等能力。除非管理員提供真實 ID，否則「團隊 ID」留白。
4. 在「模型設定」中繼承組織預設，或選擇已設定的覆寫。確認有效模型是預期的供應商與模型，再選擇「建立 Agent」。

Agent 應以可用狀態顯示在此專案名錄中。為其他專案建立 Agent 前，先確認目前選取的專案。Agent 身分和 Runtime 身分與人員登入不同；授予成員的專案權限不會自動授予 Agent。平台會將範圍受限的 Agent 憑證交給 Runtime，以執行獲准的 Run。

## 依照明確規格建立任務 {#create-task}

開啟「任務」，選擇「新增任務」。以下是可直接完成的合成練習，不需要 API、外部系統或公司資料。在「合成練習資料」區塊複製 8 行內容到「輸入資料」。

### 合成練習資料 {#practice-background}

```text
合成練習，僅供操作示範：以下是虛構資料，不需要 API 或外部來源。
產品：Northstar 練習版；上線日期：尚未確認。
產品：發布範圍與負責人尚未提供；請確認；負責人未指派。
登入：目前登入設定與驗證證據尚未提供；狀態未知。
備份：備份負責人、最近一次備份紀錄和還原證據尚未提供；狀態未知。
文件：需要草擬發布說明；文件負責人和目前文件連結未指派。
支援：支援負責人、服務時段與升級聯絡方式尚未提供；狀態未知。
分析：成功指標、事件對照和儀表板證據尚未提供；狀態未知。
```

這組資料刻意保留未知資訊；不要補造日期、負責人、核准或測試結果。

| 任務欄位 | 可複製的範例 |
| --- | --- |
| 任務名稱 | `整理產品上線清單` |
| 描述 | `為預定的產品上線準備一份可供審查的清單。` |
| 目標 | `整理上線準備工作、負責人、狀態與證據，讓審查者能判斷發布前還有哪些待辦。` |
| 輸入資料 | 複製上方「合成練習資料」的 8 行內容。 |
| 範圍 | `以已提供的合成練習資料為來源，為產品、登入、備份、文件、支援和分析各寫一行清單。每行都要包含項目、負責人、狀態和下一步行動。` |
| 限制條件 | `不得編造負責人、日期、核准或完成狀態。不得更改上線計畫或外部系統。不得包含憑證或個人資料。` |
| 驗收條件，每行一項 | `清單各包含產品、登入、備份、文件、支援和分析六個領域。`<br>`每項都有負責人，或明確標示為未指派。`<br>`每項狀態都有來源支持，或標記為未知。`<br>`每個未完成事項都有下一步行動。`<br>`提交結果包含清單以及審查所需的連結或引用證據。` |
| 優先級 | `一般` |
| 負責 Agent | 留白，或選擇 `Launch checklist worker`。單純指派不會啟動 Run。 |
| 指定審核者 | 若由有權限的人員管理者、審核者或管理員審查，請留白。 |
| 相依任務 | 除非必須先接受其他任務，否則留白。 |

選擇「建立任務」。任務應以待執行狀態出現在清單中。開啟任務，先確認目標和驗收條件，再派發。任務抽屜分為「規格」、「執行與審核」、「協作」和「事件」檢視。

![任務規格與執行控制](/screenshots/task-zh-TW.png)

### 工作依賴其他任務時新增前置條件 {#task-dependencies}

先建立前置任務，例如「確認上線日期與發布範圍」，並說明哪些證據可以證明它已獲接受。編輯清單任務，在「相依任務」選取該前置任務；提示文字是「選擇必須先完成的任務」。前置任務獲接受前，依賴它的任務不能認領或派發。前置任務獲接受後，符合條件的後續任務會解除阻塞並進入待執行。不要建立循環相依。

## 派發 Agent 並檢視 Run {#dispatch-and-run}

有權限的 Work 管理者或管理員開啟待執行任務，在「選擇 Pi 執行 Agent」中選擇 `Launch checklist worker`，再按「派發給 Agent」。這會建立自動 Run。「認領任務」是人工路線，不會啟動自動 Run。

開啟「Run 執行」並選取新 Run。檢查狀態、進度、事件、回覆、工具，以及回報的模型／用量收據。真實供應商呼叫應在 Run 記錄中標明設定的模型。如果 Run 顯示 DEMO，請停止將其回覆視為上線證據；改用人工路線或先設定模型。

Run 完成和任務驗收是兩件事。只有任務已有提交結果、至少一項證據成果物，而且狀態為「待審核」，才可進入審核。若 Run 結束時沒有提交證據，就尚未準備好審查；Worker 必須透過任務執行流程提交摘要和證據。

![Run 詳情與事件記錄](/screenshots/run-zh-TW.png)

## 提交並獨立審查證據 {#submit-review}

提交者提供簡潔的完成摘要和至少一項證據，例如文件、檔案、網址或測試報告。任務會進入「待審核」。開啟任務的「執行與審核」檢視，逐項比對驗收條件、提交成果和來源。

具備 Work「審核者」、「管理者」或組織管理員權限且不是提交者的人員，選擇「通過」或「退回」，輸入審核意見並確認。通過後任務會變成「已完成」，也可能解除後續任務的阻塞。退回會保留提交內容和歷程；在相依任務都完成後，原任務會回到待執行。提交者不能審查自己的成果。若要由人員審查，請將「指定審核者」留白；指定 Agent 後，審查畫面可能只允許該 Agent 對應的身分。

![獨立審查任務證據](/screenshots/review-zh-TW.png)

### 無模型 API Key 的人工路線 {#manual-route}

這是真正由人撰寫的成果，不是模型 Run。管理員在 `LAUNCH` 專案建立一個可用的「執行者」Agent，選擇「外部 Runtime」且不設定模型；此 Agent 僅用來代表範圍受限的執行者以供認領。任務的「負責 Agent」和「指定審核者」都留白。

先準備好六行清單和提交欄位內容，再認領任務。認領租約預設為 300 秒；認領後保持目前任務頁面開啟，若需要更多時間，請在到期前選擇「延長租約」。重新載入頁面不會保留此頁的租約控制資料，可能無法提交。

1. 第二位受邀成員需有此 Work 專案的「管理者」權限。開啟任務，在「選擇執行 Agent」中選擇上述 Worker Agent，再按「認領任務」。該成員使用核准的輸入資料親自完成清單。
2. 在任務執行控制中選擇「提交成果」。在「提交成果與證據」表單填寫完成摘要、將「證據類型」選為「文件」、填寫證據標題，再將下方六行清單貼到「證據內容」。至少提交一項成果物。任務狀態應變為「待審核」。
3. 由另一位獲授權的管理員開啟「執行與審核」，依照驗收條件檢查證據，留下審核意見後選擇「通過」或「退回」。管理員不能是提交者本人；人員審查時「指定審核者」保持留白。

可複製的證據內容（六個領域各一行）：

```markdown
- [ ] 產品：發布範圍與負責人待確認；負責人未指派、狀態未知；下一步是確認範圍及負責人。
- [ ] 登入：登入設定與驗證證據未提供；負責人未指派、狀態未知；下一步是取得核准的設定與證據。
- [ ] 備份：負責人、最近備份紀錄及還原證據未提供；負責人未指派、狀態未知；下一步是取得備份與還原紀錄。
- [ ] 文件：需要草擬發布說明；負責人未指派、狀態未知；下一步是指派文件負責人並提供草稿。
- [ ] 支援：負責人、服務時段及升級方式未提供；負責人未指派、狀態未知；下一步是確認支援安排。
- [ ] 分析：成功指標、事件對照及儀表板證據未提供；負責人未指派、狀態未知；下一步是確認指標及其證據。
```

提交欄位範例：摘要 `已按合成練習資料整理六個上線準備領域；未知狀態與未指派負責人均明確保留，並列出下一步。未存取外部系統，也未宣稱測試或核准已完成。`；證據標題 `Northstar 合成練習上線清單`。獨立審查者可使用意見範例：`已核對六個領域均有列出；未知狀態及未指派負責人均有保留，且每項都有下一步。這是合成練習，未宣稱測試通過。`

人工認領會記錄所選的限權 Worker Agent 和實際人工操作者，但不會建立 Pi Run 或付費模型呼叫。請勿將人員密碼或 API Key 填入任務。

## 重用 Agent 範本或工作流程 {#templates-workflows}

在 `LAUNCH` 專案開啟「自動化」。

- 在「Agent 範本」中，有權限的 Manager 或 Admin 可選擇「新增範本」，設定 key、顯示名稱、描述、Agent 角色、能力、選用模型、工具、沙箱設定檔、指令和執行限制，再選擇「建立 v1」。修改後會發佈新版本；既有版本與已建立的 Run 保留當時快照。在 Agent 名錄套用範本會把設定複製到新 Agent。範本本身不會授予專案、模型或工具權限。
- 在「工作流程」中選擇「新增流程」，定義各步驟的 key、名稱、目標、描述、相依步驟、Pi Agent 或所需能力、驗收條件與選用的獨立審查者；再選擇「建立 v1」。編輯器會檢查每個步驟是否指定 Agent 或候選能力。儲存後選擇「手動啟動」，在「流程輸入」填入本次上線資料，再確認「啟動流程」。流程會建立任務實例，每一步仍需提交證據並獨立審查。可在「執行紀錄」查看之前的實例。

要重用 Agent 的操作指令，使用範本；要重用有先後關係和審查步驟的一連串任務，使用工作流程。請見[Run 與自動化使用指南](../execution-usage.md)。

## 選用：附加 Code Pull Request {#optional-code-pr}

只有部署已設定 Code 和 Gitea 服務，或組織已將支援的儲存庫連線至 Work 時才使用。在 **Code** 中選取或建立 Code 專案，必要時建立私人儲存庫，再建立分支、提交與 Pull Request。該儲存庫和 PR 應出現在 Code 專案中。建立 Code 專案與儲存庫需要管理員權限及已設定的 Gitea 連線。

在 Code 專案選擇「新增 Project」，填入專案代碼 `LAUNCH`、名稱「產品上線準備」和描述。選擇「新增私人儲存庫」，填入儲存庫名稱 `launch-readiness` 和說明；預設會建立私人儲存庫、`main` 分支與 README。選擇「建立分支」，從 `main` 建立 `feature/launch-checklist`。選擇「提交檔案」，在「提交 UTF-8 檔案」表單填入「目標分支」、「儲存庫路徑」`docs/launch-readiness.md`、「檔案內容（UTF-8）」貼入上方六行清單，以及「提交訊息」`docs: add launch readiness checklist`。新增檔案時將「更新既有檔案時的 expected SHA」留白，再選擇「建立提交」。選擇「建立 PR」，來源分支（Head）填 `feature/launch-checklist`、目標分支（Base）填 `main`，標題填 `Add launch readiness checklist`，描述列出變更內容，最後建立 Pull Request。建立後 Code 頁面應顯示此 PR；`head`／`base` 必須是實際存在的分支。

回到 Work 任務，將 PR 網址作為「網址」證據提交，標題可寫 `Launch readiness checklist PR`。審查者可開啟 PR，將內容和檢查狀態與驗收條件比對。PR 連結只是待檢查的證據，不會自動讓 Work 任務通過。請見[Code 指南](code.md)。

## 完成與常見卡點 {#finish-and-troubleshoot}

只有成果附有證據並經獨立審查者接受，任務才算完成。任務應顯示「已完成」；依賴它的任務接著可能進入待執行。專案任務清單和總覽會反映已接受的狀態。

| 畫面狀況 | 檢查方式 |
| --- | --- |
| 專案選擇器中沒有專案 | 請 Admin 建立 Work 專案，並授予你的 Work 角色和專案範圍。 |
| 無法建立 Project、Space 或模型連線 | 建立 Project／Space 和編輯組織模型設定需要 Identity Admin。 |
| 沒有可選的 Agent | 確認可用的 Worker Agent 是在選取 `LAUNCH` 時建立，且該專案的 Runtime 已啟用。 |
| Run 標示 DEMO | Pi Agent 沒有可用模型，或 Pi Runtime 未使用已設定的模型。DEMO 不是真實交付物。 |
| 任務受阻或派發遭拒 | 檢查「相依任務」，先接受所有前置任務。 |
| Run 結束但任務不在待審核 | 在任務執行檢視確認是否有已提交的摘要和證據成果物。Run 完成不等於已提交。 |
| 審查按鈕無法使用 | 確認審查者具 Work 角色和專案範圍、不是提交者；若要由人員審查，將「指定審核者」留白。 |
| Knowledge 有連結但沒有內文 | 來源 URI 只是引用。把獲准內容加入文件正文，或使用已核准的檢索整合。 |
| Code 無法建立儲存庫或 PR | 請部署管理員確認本環境是否設定 Gitea，以及是否啟用 Code。 |

權限和團隊管理請接著閱讀[團隊設定](team-setup.md)。欄位說明請見[Work 指南](work.md)。
